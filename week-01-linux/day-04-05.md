# Day 4-5 — Linux Users, Groups, and Permissions

## Goal

Understand how Linux identifies users and groups, manage file ownership, and control file permissions.

## 1. `whoami` — Identify the Current User

**Purpose:** Displays the username of the current effective user.

```bash
whoami
```

Example output:

```text
khurram
```

Using `sudo`:

```bash
sudo whoami
```

Example output:

```text
root
```

**Key point:** `sudo whoami` displays `root` because the command runs with elevated privileges.

## 2. `id` — Display User and Group Information

**Purpose:** Displays the user's UID, primary GID, and group memberships.

```bash
id
```

Example output:

```text
uid=1000(khurram) gid=1000(khurram) groups=1000(khurram),27(sudo)
```

| Term | Meaning |
|---|---|
| UID | User ID |
| GID | Group ID |
| Groups | Groups the user belongs to |

### Understanding Group IDs

Example:

```text
4(adm), 27(sudo), 100(users)
```

- `4` is the GID of the `adm` group.
- `27` is the GID of the `sudo` group.
- `100` is the GID of the `users` group.

Linux uses numeric IDs internally to identify users and groups. These IDs may differ between systems.

## 3. `groups` — List Group Memberships

**Purpose:** Displays the groups to which a user belongs.

```bash
groups
```

To check another user's groups:

```bash
groups root
```

To inspect a specific group:

```bash
getent group sudo
```

Example output:

```text
sudo:x:27:khurram
```

This output contains the group name, password placeholder, GID, and supplementary group members.

### Create a New Group

```bash
sudo groupadd developers
```

This creates a group named `developers`, provided it does not already exist.

Verify it:

```bash
getent group developers
```

## 4. `chmod` — Change File Permissions

**Purpose:** Changes the permissions of files and directories.

```bash
chmod 644 app.log
```

### Permission Values

| Value | Permission | Meaning |
|---:|---|---|
| `4` | `r` | Read |
| `2` | `w` | Write |
| `1` | `x` | Execute |
| `0` | `---` | No permissions |

Permission values are added together:

| Value | Permissions | Calculation |
|---:|---|---|
| `7` | `rwx` | 4 + 2 + 1 |
| `6` | `rw-` | 4 + 2 |
| `5` | `r-x` | 4 + 1 |
| `4` | `r--` | 4 |
| `0` | `---` | 0 |

### The Three Permission Categories

Numeric permissions follow this order:

**Owner → Group → Others**

Example:

```bash
chmod 754 app.log
```

| Digit | Category | Permissions |
|---:|---|---|
| `7` | Owner | Read, write, execute |
| `5` | Group | Read, execute |
| `4` | Others | Read only |

### Common Examples

Owner can read and write; group and others have no permissions:

```bash
chmod 600 app.log
```

Owner has full permissions; group and others can read and execute:

```bash
chmod 755 script.sh
```

Remove all permissions:

```bash
chmod 000 app.log
```

Expected permissions from `ls -l`:

```text
----------
```

**Important:** In a numeric mode, `chmod 6 app.log` is not equivalent to `chmod 600 app.log`. A single-digit mode applies to the rightmost permission digit, so use three digits for clarity.

### Symbolic Permissions

| Symbol | Category |
|---|---|
| `u` | Owner/user |
| `g` | Group |
| `o` | Others |
| `a` | All categories |

Add execute permission for the owner:

```bash
chmod u+x script.sh
```

Remove write permission from the group:

```bash
chmod g-w app.log
```

Add read permission for others:

```bash
chmod o+r app.log
```

Add read permission for everyone:

```bash
chmod a+r app.log
```

### Useful `chmod` Options

| Option | Purpose |
|---|---|
| `-R` | Apply changes recursively |
| `-v` | Display details for processed files |
| `-c` | Report only files whose permissions changed |
| `-f` | Suppress most error messages |

Examples:

```bash
chmod -v 644 app.log
chmod -c 600 app.log
chmod -R 755 myfolder
```

**Caution:** Avoid applying `755` recursively without checking the contents. It can make regular files executable unnecessarily.

## 5. `chown` — Change File Ownership

**Purpose:** Changes a file's owner, group, or both.

### Change Only the Owner

```bash
sudo chown ali app.log
```

The owner becomes `ali`. The group normally remains unchanged.

### Change Both Owner and Group

```bash
sudo chown ali:developers app.log
```

- `ali` is the new owner.
- `developers` is the new group.
- `app.log` is the target file.

### Change Only the Group

```bash
sudo chown :developers app.log
```

The owner remains unchanged, while the group becomes `developers`.

### Change Ownership Recursively

```bash
sudo chown -R ali:developers myfolder
```

This changes ownership throughout the directory tree.

**Key point:** Changing the owner does not normally change the permission bits. However, access can change because the new owner receives the owner permissions, while the former owner is evaluated under the group or others permissions.

## 6. `chgrp` — Change the Group

**Purpose:** Changes a file's group without changing its owner.

```bash
sudo chgrp developers app.log
```

Verify the change:

```bash
ls -l app.log
```

Example output:

```text
-rw-r----- 1 ali developers 0 Oct 27 app.log
```

Here, `ali` is the owner and `developers` is the group.

The target group must exist. Create it first if necessary:

```bash
sudo groupadd developers
```

## 7. `ls -l` — Inspect Permissions and Ownership

**Purpose:** Displays file permissions, owner, group, size, and other information.

```bash
ls -l app.log
```

Example output:

```text
-rw-r----- 1 ali developers 0 Oct 27 app.log
```

Breakdown:

```text
- rw- r-- ---
  |   |   |
Owner Group Others
```

- `rw-`: Owner can read and write.
- `r--`: Group can read.
- `---`: Others have no permissions.

The first character indicates the file type:

- `-` — Regular file
- `d` — Directory
- `l` — Symbolic link

## 8. WSL and Permission Testing

If Ubuntu runs through Windows Subsystem for Linux (WSL), file location can affect permission behaviour.

- `~/app.log` is normally inside the Linux filesystem.
- `/mnt/c/...` is normally on the Windows C: drive.

Windows-mounted files may behave differently depending on WSL mount configuration.

Test permissions inside the Linux filesystem:

```bash
cd ~
touch app.log
chmod 000 app.log
ls -l app.log
cat app.log
```

A normal user should receive `Permission denied` when trying to read this file.

If access is still possible, check:

```bash
whoami
id
pwd
ls -l app.log
```

The `root` user can generally bypass ordinary file permission restrictions. On Windows-mounted files, the mount configuration may also affect the result.

## Problems and Solutions

### Problem 1: I can still read a file after `chmod 000`.

**Possible causes:**
- The command is running as `root`.
- The file is on a Windows-mounted filesystem.
- The file path or permissions are not what you expected.

**Solution:** Check `whoami`, `pwd`, and `ls -l`. Repeat the test with a file created inside `~`.

### Problem 2: The group change fails.

**Possible cause:** The specified group does not exist.

**Solution:**

```bash
getent group developers
sudo groupadd developers
sudo chgrp developers app.log
```

Only run `groupadd` if the group does not already exist.

## What I Learned

- Linux identifies users and groups using numeric IDs.
- `whoami`, `id`, and `groups` provide different identity information.
- `chmod` controls read, write, and execute permissions.
- Numeric permissions follow the Owner → Group → Others order.
- `chown` changes ownership, while `chgrp` changes the group.
- `ls -l` helps verify permissions and ownership.
- WSL filesystem location can affect permission behaviour.
